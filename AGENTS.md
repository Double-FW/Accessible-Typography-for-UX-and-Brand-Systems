# AGENTS.md

This repository is a knowledge base on accessible typography for UX and brand systems. This file defines the operating rules for AI agents, editors, and reviewers working in this repository.

This document is advisory and repository-local. It is not an executable policy engine, a deployment configuration, a compliance system, or a guarantee that any external service or human approval process exists. The repository does not currently include a runtime enforcement mechanism for these instructions, so they should be treated as a decision aid and review standard.

## 1. Purpose and audience

This file applies to AI assistants and human contributors who:

- write or revise typography guidance in this repository;
- evaluate or compare typefaces, type systems, or editorial approaches;
- draft brand, marketing, communication, or publishing recommendations based on the repository’s material; and
- support review of content that affects readability, accessibility, or brand communication.

It does not authorize external publishing, deployment, legal claims, compliance assertions, or operational actions beyond the repository itself.

## 2. Scope

This repository is primarily a content and synthesis project. The instructions below therefore focus on:

- evidence-based typography guidance;
- clear separation of evidence, assumption, and inference;
- readable and maintainable repository content; and
- human accountability for consequential recommendations.

This file does not define application or deployment behaviour for a production system unless a future repository implementation explicitly adds it.

## 3. Authority and conflict resolution

When instructions conflict, apply the following order:

1. Repository-local content and explicit repository conventions.
2. More specific instructions that apply to a narrower task or directory.
3. User instructions that are compatible with the repository and do not contradict the repository’s stated purpose.
4. General best practice, when no repository guidance covers the issue.

If a requirement is missing, unknown, or not supported by evidence, the agent MUST say so explicitly. It MUST NOT invent approvals, enforcement, services, credentials, owners, or review processes that do not exist in the repository.

## 4. Required operating behaviour

Agents working in this repository MUST:

- write in plain, direct language;
- distinguish between evidence, assumptions, and conclusions;
- state the audience, task, language or script, and reading context before making a substantive typography recommendation;
- separate emotional accessibility, functional accessibility, and technical accessibility;
- cite the repository’s material and avoid presenting unverified claims as settled fact;
- identify unresolved risks, unknowns, and missing evidence; and
- require human review for brand-critical or consequential recommendations when evidence is incomplete or the stakes are high.

Agents MUST NOT:

- claim that a single typeface or style is universally accessible;
- present serif or sans serif as a universal rule;
- treat preference as equivalent to accessibility;
- infer disability or reading condition from a person’s font choice or preference;
- recommend decorative display type for body text or important instructions;
- ignore language, script, glyph coverage, fallback behaviour, or shaping requirements;
- claim validation, approval, or compliance without evidence in the repository or a clearly identified source;
- invent repository capabilities, infrastructure, security controls, or operational services.

## 5. Evidence standard

Typography guidance in this repository should be interpreted as a system-level decision, not as a fixed aesthetic preference.

Before making or approving a recommendation, agents should establish:

- who the audience is;
- what task the text supports;
- which language and script are in scope;
- where the text will be read and under what conditions;
- whether the concern is emotional, functional, or technical accessibility; and
- what evidence supports the recommendation.

If the evidence is weak, incomplete, or missing, the recommendation must be labelled provisional or incomplete. Do not silently convert uncertainty into certainty.

## 6. Decision framework

Use this checklist when producing or reviewing guidance:

1. Audience and task
2. Language and script requirements
3. Reading context and device conditions
4. Emotional, functional, and technical considerations
5. Recommended type treatment or typeface choice
6. Evidence and testing status
7. Risks, unresolved questions, and human review needs

For high-impact or brand-defining typography decisions, the agent should ask for human review when evidence is limited or when the recommendation has a meaningful impact on trust, comprehension, or accessibility.

## 7. Human review and escalation

Humans remain the decision owner for consequential or reputational judgments. The agent SHOULD escalate when:

- a recommendation affects brand trust or external communication;
- the language, script, or audience is under-specified;
- the content is high-risk, unclear, or safety-relevant;
- evidence is missing or conflicting; or
- a claim could be interpreted as a guarantee of accessibility or compliance.

The agent MUST clearly state what is known, what is uncertain, and what decision remains with a human reviewer.

## 8. Output expectations

When responding in this repository, prefer a structure such as:

- Audience and task
- Language and script requirements
- Context and constraints
- Recommendation
- Evidence status
- Risks and unresolved questions
- Human review trigger, if any

Responses should be explicit about uncertainty and should not imply that a recommendation is final when it is only provisional.

## 9. Repository fit and maintenance

This file is intended to be concise, readable, and easy to update. Keep it aligned with actual repository contents and avoid referencing nonexistent systems, tooling, or governance processes.

The project is a knowledge-base repository, not a production application. This means the guidance is strongest when it is practical, evidence-aware, and explicit about its limits.

## 10. Short version

A well-scoped AI agent in this repository should:

- work inside the repository’s purpose;
- prefer evidence over style preference;
- define context before recommending type;
- separate facts from assumptions;
- keep uncertainty visible;
- avoid unsupported guarantees; and
- route consequential decisions to a human reviewer.

This is the operational core of the repository guidance.
